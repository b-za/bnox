## Core Concepts (5-Minute Overview)

### Project
A container for related work. Has an index note (`type: project`) that lists:
- Jobs (via `project: "id"` in job frontmatter)
- Sessions (via `project: "id"` in session frontmatter)
- Decisions (via `project: "id"` in decision frontmatter)

**Project index auto-regenerates** via `tools/scripts/project-index --project <id> --write`

### Job
Rich work item with **agreed scope** (unlike `todo` which is vague).
- `type: job`
- `status`: `open` | `in-progress` | `done` | `blocked`
- `project`: links to project
- `session`: optional, assigned session
- `depends_on`: other job IDs

### Session — What It Is
A **session** is a persisted record of a single agent conversation. When you (an agent) boot up, you start a new conversation. That conversation gets a session record created by `session-start` and closed by `session-end`.

**What a session IS:**
- A persisted record of one agent conversation
- Created by `session-start` (sets `session_started`)
- Closed by `session-end` (sets `session_ended`, marks `completed`)
- Has an ID = filename = timestamp+suffix (e.g., `260831120000-EGMB.md`)
- Has `alias` for human reference (e.g., "Morning Parse Session")
- Links to a `project` and optionally a list of `jobs`
- Has `handover` pointing to a note with the order of attack for the next agent
- Has `previous_session` / `next_session` links forming a chain

**What a session is NOT:**
- ❌ A persistent process or background job (it's a record, not a running thing)
- ❌ A long-running server or daemon
- ❌ The agent itself (you are the agent; the session is the record of your conversation)
- ❌ A container that holds jobs (jobs exist independently; a session just *references* jobs it worked on)
- ❌ Something that persists across agent restarts (each boot = new conversation = new session)

**Session lifecycle:**
1. `session-start --session-id <id> --write` — creates record, sets `session_started`
2. You do work (the conversation happens)
3. `session-end --session-id <id> --write` — sets `session_ended`, adds `completed` tag

### The Session Note — What It Is
A **session note** is the markdown file that serves TWO purposes:

**1. Planning Document (Before/At Session Start)**
- Created by `session-start` with basic metadata
- You (the agent) EDIT it to add:
  - Links to jobs this session will focus on (`jobs:` list)
  - Link to the project (`project:` field)
  - Narrative context: what's the goal? what's the plan?
  - Any setup/prerequisites
- This becomes your "session plan"

**2. Close-Out Report (At Session End)**
- At close-out, you EDIT the same note to add:
  - Brief narrative: what was done? what changed?
  - What worked / what didn't
  - Blockers encountered
  - Decisions made (link to decision notes)
  - Follow-up items (link to jobs, create new jobs/todos)
  - Handover for next agent (order of attack)
- Then run `session-end` to close it

**The session note is the single source of truth for that conversation.**
It starts as a plan, becomes a record.

### Job
Rich work item with **agreed scope** (unlike `todo` which is vague).
- `type: job`
- `status`: `open` | `in-progress` | `done` | `blocked`
- `priority`: `high` | `medium` | `low`
- `project`: links to project
- `session`: optional, assigned session
- `depends_on`: other job IDs

### Todo vs Job vs Open-Question
| Type | Purpose | Scope |
|------|---------|-------|
| `job` | Agreed scope, just scheduling/execution | Clear |
| `todo` | Vague, open-ended, needs clarification | Fuzzy |
| `open-question` | For human-agent discussion | Discussion |

## Working Rules (Non-Negotiable)

1. **Every decision gets a decision note** with losing readings + triggers
2. **Every session gets a handover** with order of attack
3. **Every job gets a scope agreement** before starting
4. **Spec-validate must pass** before committing
5. **Generated content only in GENERATED fences** - never overwrite authored prose
6. **Decision notes are immutable** - add new decisions, don't edit old ones
