## Principles

1. **One Concern Per File** — Split by data flow layer (input, processing, output)
2. **Explicit Connections** — Use `HAS_CHILD`, `NEXT_SIBLING`, `REFERENCES` edges
3. **Machine-Readable Frontmatter** — Structured metadata for tooling
4. **Human-Readable Body** — Narrative, diagrams, examples
5. **Timestamped IDs** — All files use `260825144502-DFSF.md` format
6. **Decision Files Are the Conventions** — The decision files (types decision-how/decision-corpus, alternative-how/-corpus, trigger-how/-corpus, todo, question-how/-corpus) ARE the conventions. All other documents point to them by ID.
7. **Boot Prompts Reference Only Decision Files** — Boot prompts contain only file IDs and reading order. Never include convention summaries, tables, definitions, or "quick references". The decision files ARE the conventions; everything else is an address to them.
8. **Measure, Never Quote (narrowed)** — A claim about current state that will change (counts of notes, records, actions "now") must name its instrument (e.g. "counted by `grep -c '^id:'`") or be dated ("as of v8: 31 actions"). Exempt: settled values that are themselves the decision (caps, ranges, contract versions), observations from a dated event, and counts in a session note's record. See [[docs/graph/261111224703-D003|Counts rule narrowed to claims about current state]] (bnox-bg D034).
9. **Generated/Authored Separation** — Hybrid notes use explicit HTML comment fences: `<!-- GENERATED:START:unique-id -->...<!-- GENERATED:END:unique-id -->`. Generators rebuild ONLY between fences; they exit if no fence exists. Generators never write into authored prose outside fences.
10. **Never Overwrite Authored Artefacts** — Generators never overwrite files with human/agent edits, except within their designated fence. A note is authored from its first write.
11. **Index = Address, Not Currency Guarantee** — Index files list IDs as addresses. Read the index to find the address, then search forward for newer decisions that might have changed it. Index files include a disclaimer to this effect.
12. **What This Does Not Do** — Every section states what it does NOT do (what was not created, edited, decided, banked). Makes omissions visible rather than reading as oversight.
13. **Three-Tier Rule Enforcement** — Rules classified as: deterministic script (`tools/scripts/`), agent-checkable (`tools/checks/`), or guideline. Scripts exit 0 on pass, non-zero on fail with descriptive output.
14. **Primary Register** — `grep -r '^id:'` is the source of truth for all note IDs. Docs write `(id)` to avoid polluting the register.
15. **Boot Set & Close-Out Protocol** — Session entry reads ordered boot set. Close-out includes: decisions captured with losing readings, context sweep, state docs current, index entries added, audit index gaps, re-measure, decisions vs findings, decisions reached destination, log findings.
16. **Context Sweep** — Enumerate: conflicts not raised, silent judgements, deferred options, stale notes, "anything else on mind?". Stop when no new items since last pass.
17. **Finding Notes** — Agents log observations needing review: `type: "finding-how"` or `"finding-corpus"`, typed fields `status` (open/review/resolved/archived), `category` (investigation/anomaly/pattern/concern/opportunity), `severity` (low/medium/high/critical), plus `context`, `related`, `evidence`, `aliases`. Created during work and close-out.

## Decision / Alternative / Trigger Note Types

A **decision** is a settled choice that affects behaviour, a contract, a convention or our process, or anything the person states as a ruling ([[docs/graph/261111224703-D003|What counts as a decision]] (bnox-bg D008)). Every decision gets a note; implementation details belong in code and commits.

### Decision Notes (`type: "decision-how"` | `"decision-corpus"`)

```yaml
id: "YYMMDDHHMMSS-XXXX"
type: "decision-corpus"
title: "Human readable title"
aliases: ["Decision Name", "Short Alias"]
tags: ["filters", "sentinels"]      # subject words only
authority: "ruled-by-person"        # or "judgement-by-agent"
project: "project-id"
supersedes: ["older-decision-id"]   # when it replaces one (two-way, see below)
```

**Required sections:** `## Decision`, `## Alternatives Considered`, `## Losing Readings`, `## Glossary Implications`, `## Consequences Elsewhere`, `## Review Triggers`, `## Related Decisions`, `## What This Does Not Do`. When nothing was raised, a section says so ("None — no alternative was raised").

### Alternative Notes (`type: "alternative-how"` | `"alternative-corpus"`)

Written only for an option that was actually raised — never invented ([[docs/graph/261111224703-D003|Alternative and trigger notes only when they really exist]] (bnox-bg D010)). Body: losing reading, revival trigger, link back to the decision(s). Reusable across decisions via `aliases`.

### Trigger Notes (`type: "trigger-how"` | `"trigger-corpus"`)

Written only for a real review condition. Body: condition, action, link back to the decision(s).

### Authority (`authority` field)

- `ruled-by-person` — an explicit ruling by the person; passing remarks or thinking out loud never become rulings.
- `judgement-by-agent` — settled by the agent, including when the person was asked and said "you decide" ([[docs/graph/261111224703-D003|Only explicit rulings are ruled-by-person]] (bnox-bg D009)).

### Superseding

A decision that replaces another lists `supersedes: [ids]`; the replaced note gets `superseded_by: [ids]` and a DEAD marker on the replaced claim ([[docs/graph/261111224703-D003|Superseding is recorded with two-way links plus a stale-reference check]] (bnox-bg D012)). At close-out the session note records each new decision's supersession search ([[docs/graph/261111224703-D003|Close-out records each new decision's supersession search]] (bnox-bg D046)).

## Dead Text Marking

Use HTML comments to mark superseded text kept for traceability:

```markdown
<!-- DEAD: superseded by [[docs/graph/260825144502-DFSF]] -->
Old claim that was superseded.
<!-- /DEAD -->

New claim replacing it. See [[docs/graph/260825144502-DFSF]].
```

Format: `<!-- DEAD: superseded by [[id]] -->old<!-- /DEAD -->`
Names the decision that killed it. Acts as a "vaccine" against re-proposing the same error.

## Generator CLI Pattern

All deterministic scripts in `tools/scripts/` follow this interface:

```bash
script-name [--write] [--output-path <path>] [--help]
```

- **Default:** Print results to stdout
- **`--write`:** Write results to default output file (`script-name-results.txt`)
- **`--output-path <path>`:** Write results to custom path (implies `--write`)
- **Exit codes:** 0 = pass, non-zero = fail with descriptive output
- **Generated content:** Only between HTML comment fences `<!-- GENERATED:START:unique-id -->...<!-- GENERATED:END:unique-id -->`
- **Never overwrite authored content** outside fences

## What This Does Not Do (Meta)

This guide does not:
- Define specific domain decisions (architecture, product, etc.)
- Mandate specific tooling languages
- Specify CI/CD integration
- Define retention/archival policies for findings or dead text

## Decision Domains

Two domains ([[docs/graph/261111224703-D003|Two domains, carried by the type suffix: how we work / what we are working on]] (bnox-bg D035)), carried by the note type's suffix — no domain tag:

| Domain | Suffix | What it is |
|--------|--------|------------|
| **How we work** (meta-procedure) | `-how` | Procedures, rules, conventions, checks |
| **What we are working on** (subject matter) | `-corpus` | The repo's own subject: here, the bnox NixOS base |

**Where things live** ([[docs/graph/261111224703-D003|Operational hows live in tools/; the decisions behind them live in docs/graph]] (bnox-bg D036)): operational hows — the current "what to do" — live in `tools/` (here `tools/meta`); the decisions that explain how a how came to be live in `docs/graph` as `decision-how` notes, linked from the how. Subject-matter decisions live in `docs/graph` as `decision-corpus` notes.

How-decisions are usually the person's to rule and change rarely; subject-matter decisions change with evidence.

## Splitting a Component Spec

The splits below are the norm, offered as suggestions; a repo may deviate, but only as an explicit choice by its user, recorded as a decision ([[docs/graph/261111224703-D003|The base's spec-splitting guidance is the norm; deviations are explicit user choices]] (bnox-bg D040)). bnox-bg's choice: [[docs/graph/261111224703-D003|bnox-bg's spec split: per command family, per convention, per host module]] (bnox-bg D041). Filenames stay timestamp IDs — the `X.input.md` names below are labels, not filenames.

### By Data Flow Layer

For component `X`:
- `X.input.md` — Inputs, triggers, schemas, sources
- `X.processing.md` — Algorithms, transformations, rules
- `X.output.md` — Outputs, events, guarantees, contracts

### By Concern (Alternative)

- `X.interface.md` — Public API, NATS subjects, payloads
- `X.implementation.md` — Internal logic, data structures
- `X.testing.md` — Test cases, fixtures, properties

### Choosing Split Strategy

| Component Type | Recommended Split |
|----------------|-------------------|
| Pipeline stage (parser, diff) | Data flow layers |
| Infrastructure (KV writer, fsnotify) | Interface / Implementation |
| Cross-cutting (config, health) | Single file |

## Modeling Connections

### Edge Types for Spec Relationships

| Edge | Source | Target | Meaning |
|------|--------|--------|---------|
| `HAS_CHILD` | Parent spec | Child spec | Hierarchy (e.g., parser → parser.input) |
| `NEXT_SIBLING` | Spec A | Spec B | Sequential flow (input → processing → output) |
| `REFERENCES` | Spec A | Spec B | A depends on B's output/contract |
| `IMPLEMENTS` | Impl spec | Interface spec | Implementation satisfies interface |
| `TESTS` | Test spec | Target spec | Tests validate target |

### Frontmatter for Connections

```yaml
connections:
  - type: "HAS_CHILD"
    target: "260825144504-DFSH"
  - type: "NEXT_SIBLING"
    target: "260825144505-DFSI"
  - type: "REFERENCES"
    target: "260825144509-DFSM"
```

## Writing Guidelines

### Frontmatter Required Fields

```yaml
id: "260825144502-DFSF"  # Full node ID, matches filename stem
type: "spec|adr|concept|narrative|guide|check|alternative|trigger|decision|todo|open-question|runbook|contract|index|integration|test-spec|ui-spec|threat-model|perf-plan|migration|config-ref|boot-set|job|session|project"
title: "Human readable title"
aliases: ["Primary Alias", "Secondary Alias"]  # At least one required
tags: ["subject", "words"]  # What the note is about; no # prefix; reuse existing tags
```

### Frontmatter for Job Notes (`type: "job"`)

```yaml
id: "260831120000-EGLA"
type: "job"
aliases: ["Job Name", "Short Alias"]
tags: ["subject", "words"]
status: "open"  # open | in-progress | done | blocked
priority: "high"  # high | medium | low
depends_on: ["job-id-1", "job-id-2"]  # optional, job dependencies
project: "project-id"  # optional, project scope
session: "session-id"  # optional, assigned session
context: "[[decision-id]]"  # wiki link to decision/file
```

**Job vs Todo**: Job = scope agreed, just scheduling/execution. Todo = open-ended, vague, needs clarification.

### Frontmatter for Session Notes (`type: "session"`)

```yaml
id: "260831120000-EGLB"  # timestamp+suffix, used as session ID
aliases: ["Session Name", "Short Alias"]  # for conversation
tags: ["subject", "words"]
status: "planned"  # planned | active | completed
jobs: ["job-id-1", "job-id-2"]  # jobs to execute in this session
previous_session: "session-id"  # optional, previous session
next_session: "session-id"  # optional, next session
handover: "note-id"  # optional, link to handover note
order: 1  # integer for session index ordering
project: "project-id"  # optional, project scope
session_started: "2026-08-31T12:00:00Z"  # set by session-start script
session_ended: "2026-08-31T14:30:00Z"  # set by session-end script
```

**Session ID**: ID = filename (timestamp+suffix). **Alias**: for conversation reference.
**Timestamps**: `session_started` set by `tools/scripts/session-start`, `session_ended` set by `tools/scripts/session-end` at close-out.
**Session Indexes**: Two per project — **Generated** (old/completed, auto-rebuilt from `type:session`) and **Planned** (future, manually curated).

### Frontmatter for Project Notes (`type: "project"`)

```yaml
id: "260831120000-EGLC"
type: "project"
aliases: ["Project Name", "Short Alias"]
tags: ["subject", "words"]
status: "active"  # active | archived
# Generated sections below — updated by `tools/scripts/project-index --project <id>`
```

**Generated sections** (code-generated via `tools/scripts/project-index --project <id>`):

```markdown
<!-- GENERATED:START:example-project-jobs -->
- [[job-id-1|Job Name 1]]
- [[job-id-2|Job Name 2]]
<!-- GENERATED:END:example-project-jobs -->

<!-- GENERATED:START:example-project-sessions -->
- [[session-id-1|Session Name 1]]
- [[session-id-2|Session Name 2]]
<!-- GENERATED:END:example-project-sessions -->

<!-- GENERATED:START:example-project-decisions -->
- [[decision-id-1|Decision Name 1]]
- [[decision-id-2|Decision Name 2]]
<!-- GENERATED:END:example-project-decisions -->
```

Jobs/sessions/decisions linked via `project: "project-id"` in their frontmatter.

### Frontmatter for Index Notes (`type: "index"`)

**Generated (Old/Completed Sessions)**

### Body Structure

1. **Overview** — One paragraph summary
2. **Detailed Sections** — Numbered, with code/tables
3. **Guards/Invariants** — What must always be true
4. **Failure Modes** — What can go wrong, mitigations
5. **See Also** — Wiki links to related specs

### Boot Prompt Rule

When creating boot prompts (or any document that references conventions):

1. **Read the decision files first** — extract IDs, do not rely on memory
2. **Write only references** — file IDs and reading order only
3. **Never include convention summaries** — no tables, definitions, "quick references", or "key conventions" sections
3. **Decision files ARE the conventions** — boot prompts contain only file IDs and reading order

The decision files ARE the conventions; everything else is an address to them. No summaries, cheat sheets, or "quick references" — they all drift.
