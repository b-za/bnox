# Diversions pattern

**Phase 6 deliverable.** Specifies how a host diverges from the bnox base. A host config is a thin file (~30 lines) that expresses *only* the per-machine divergence — everything else is inherited from `modules/` (see `06-base-design.md`). Implementation follows once the structure is confirmed.

## Resolved structural choices (this session)

| # | Choice | Resolution |
|---|---|---|
| Q-D1 | Profile selection mechanism | **A — explicit import.** Profiles and hardware modules exposed as flake outputs (`bnox.profiles.<name>`, `bnox.hardware.<name>`); host does `imports = [ bnox.profiles.desktop ]`. No attribute-based dispatch. |
| Q-D2 | Host enumeration in flake | **B — auto-discovery.** `flake.nix` reads `hosts/*/`, builds a `nixosSystem` config per subdir. Adding a host = adding a dir; no `flake.nix` edit. |
| Q-D3 | Profile set | **3 profiles: `minimal`, `server`, `desktop`.** `minimal` kept (genuinely different from base — bootstrap/first-boot with no Tailscale/user; matches snowi-node's `configuration-minimal.nix`). Recorded as a lean not separately confirmed; flag on review if you'd rather drop it. |

## Diversion axes (3, orthogonal)

| Axis | Cardinality | What it controls | Where declared |
|---|---|---|---|
| **Profile** | exactly one of `minimal` / `server` / `desktop` | GUI/software divergence (headless vs desktop) | host imports one |
| **Hardware** | zero or more | kernel modules, peripherals, firmware (e.g. broadcom wifi) | host imports as needed |
| **Things** | zero or more | which things run here + their bindings | `bnox.things.<name>` in host config |

`modules/base/` is the implicit floor every host inherits (SSH hardening, user `bh`, firewall defaults, Tailscale, base packages, home-manager). Profiles diverge from that floor; they do not replace it. Per-host one-offs (hostname, network type, firewall exceptions) live in the host file directly.

## Profiles

| Profile | Adds / diverges from base | Use case |
|---|---|---|
| `minimal` | Trims: disables Tailscale, defers user setup, no things. Just SSH + root + basic networking. | nixos-anywhere first-boot (FR-1.2). Rebuilt into a real profile once provisioned. |
| `server` | Near-empty additive. Base is already server-friendly; `server` is mostly the *absence* of desktop (no GUI packages, no X). | VPS / headless hosts (snowi-node's trajectory). |
| `desktop` | Adds: X server, qtile, ly display manager, terminal, browser, audio. (uqbn's territory, FR-12.2.) | Laptops / workstations (uqbn's trajectory). |

`minimal` imports base then trims via `lib.mkForce`/`enable = false`; it does not bypass the base code path. Keeps one architecture for all hosts.

Hardware modules live in `modules/hardware/` (empty day-1) and are exposed as `bnox.hardware.<name>`. A host imports zero or more. Orthogonal to profile: a MacBook is `desktop` profile + `macbook-broadcom-wifi` hardware module; a VPS is `server` profile + (usually) no hardware module (cloud hardware comes from the generated `hardware-configuration.nix`).

## Host config shape (~30 lines)

The host file expresses *only* divergence. The bnox base module is injected by the flake (see enumeration below), not re-imported per host.

```nix
# hosts/<name>/configuration.nix
{ bnox, ... }:
{
  imports = [
    bnox.profiles.desktop                  # exactly one: .minimal / .server / .desktop
    bnox.hardware.macbook-broadcom-wifi    # zero or more (omit if none)
    ./hardware-configuration.nix           # generated by nixos-generate-config
    ./disk-config.nix                      # disko, hand-written
    ./secrets/secrets.nix                  # agenix rules, local per choice 4a
  ];

  networking.hostName = "<name>";
  networking.wireless.enable = true;       # network type is host-local: DHCP / static / wifi

  bnox.things.hermes = {                   # thing bindings (D-006, Q9.5)
    enable = true;
    source = "/srv/hermes";
  };

  networking.firewall.allowedTCPPorts = [ 80 443 ];  # host-specific extras
}
```

What belongs here vs. elsewhere:

| In host config | In `modules/` (base/profile/platform/things) |
|---|---|
| hostname | SSH hardening |
| network type (DHCP/static/wifi) | user `bh`, base packages |
| profile + hardware selection | firewall defaults |
| thing enable + bindings (`bnox.things.*`) | all platform services |
| local `hardware-configuration.nix` + `disk-config.nix` | thing abstraction + hardening |
| local agenix rules | secrets backends |
| host-specific firewall ports / extra packages | deployment pipeline |

## Flake host enumeration (auto-discovery)

`flake.nix` reads `hosts/` and builds one `nixosSystem` per subdir. The bnox base module is injected here so host files stay divergence-only. `bnox` is passed as a specialArg so host configs can reference `bnox.profiles.*` / `bnox.hardware.*`.

```nix
# flake.nix (sketch)
nixosConfigurations = let
    hostNames = builtins.attrNames (builtins.readDir ./hosts);
  in builtins.listToAttrs (map (name: {
    inherit name;
    value = nixpkgs.lib.nixosSystem {
      system = "x86_64-linux";
      specialArgs = { bnox = self; };
      modules = [
        self.nixosModules.bnox              # base injected, not re-imported by host
        ./hosts/${name}/configuration.nix
      ];
    };
  }) hostNames);
```

External consumers (a separate repo using bnox as a flake input) follow the same shape: `specialArgs = { bnox = bnox; }` where `bnox` is the input, and import the consumer's own host config. Same pattern, different `bnox` binding.

## Worked examples

### Example 1 — VPS server host (snowi-node successor trajectory)

```nix
# hosts/<vps-name>/configuration.nix
{ bnox, ... }:
{
  imports = [
    bnox.profiles.server
    ./hardware-configuration.nix           # cloud provider's generated config
    ./disk-config.nix
    ./secrets/secrets.nix
  ];

  networking.hostName = "<vps-name>";
  networking.useDHCP = false;
  networking.interfaces.enp6s18.ipv4.addresses = [ { address = "..."; prefixLength = 24; } ];
  networking.defaultGateway = "...";

  bnox.things.<app> = { enable = true; source = "/srv/<app>"; components = { ... }; };

  networking.firewall.allowedTCPPorts = [ 80 443 ];
}
```

### Example 2 — MacBook desktop host (uqbn successor, D-012 Phase 3)

```nix
# hosts/<laptop-name>/configuration.nix
{ bnox, ... }:
{
  imports = [
    bnox.profiles.desktop
    bnox.hardware.macbook-broadcom-wifi    # lands in Phase 3, tested on 26.05
    ./hardware-configuration.nix
    ./disk-config.nix
    ./secrets/secrets.nix
  ];

  networking.hostName = "<laptop-name>";
  networking.wireless.enable = true;

  bnox.things.hermes = {                   # D-009 — first thing on the post-wipe MacBook
    enable = true;
    source = "/srv/hermes";
  };
}
```

## Provisioning flow (reference; detailed in Phase 3)

1. Generate `hardware-configuration.nix` on the target via `nixos-generate-config` (or live USB — see risk note in `06-base-design.md`).
2. Hand-write `disk-config.nix` (disko).
3. Write the ~30-line `configuration.nix` picking profile + hardware + thing bindings.
4. `nixos-anywhere` installs: disko partitions, copies config, injects SSH host key (D-008), reboots into `minimal` or the chosen profile.
5. Subsequent changes via `nixos-rebuild`; NixOS generations are the rollback safety net (every rebuild is a boot-menu entry).

A bnox wrapper script automating steps 1–3 (collect hardware info, emit host skeleton) is a Phase 2/3 deliverable, not Phase 6.
