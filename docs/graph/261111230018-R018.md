# NATS identity: logins always, two-level permissions, roles (series 0.4)

Converted from the archived decision log ([[docs/graph/261111230000-D005|converted archive decisions]]): `docs/archive/design/process/05-decisions.md` line 545, D-018 (accepted (implementation: 0/4/0)).

## Context

bnox's broker is open ([[docs/graph/261111230006-R006|Thing hosting architecture]] L0); L1 (per-thing users) was designed-for. agenthub built its own lockdown: per-service nkeys generated on the host (`nkey.py`, keygen unit), per-service permission files, a runtime assembler writing the auth config (G12). bnox 0/3/0 ships an implied `nats_seed` slot that nothing in bnox fills, and its pipeline units break the moment the broker requires logins (G23, G4). agenthub also used its own subject layout (`agenthub.<worker>...`, one shared stream) — improvised, not reasoned against [[docs/graph/261111230006-R006|Thing hosting architecture]].

## Decision

1. **NATS logins are always required.** No anonymous user. Not opt-in.
2. **Subject layout stays [[docs/graph/261111230006-R006|Thing hosting architecture]]:** `host.>` bnox-owned, `things.<name>.>` per thing, one JetStream stream per thing. Hosts fit custom structure beneath a thing's prefix (agenthub moves onto it).
3. **Two-level permissions; the final grant is what both levels allow (intersection):**
   - **Host level** decides who may talk to whom (from `deps` / explicit grants — e.g. che → gsheet), as a ceiling.
   - **Thing level** (`.bnox/`) declares what the thing offers to others (e.g. publish `command.>`, subscribe `event.>`) — so no host grant can let another identity publish fake events for it.
4. **Roles:** a thing's `.bnox/` may declare named roles (e.g. `user`, `admin`) as subsets of its offer; the host assigns a role per dependent. NATS enforces them (a non-admin cannot even publish an admin command).
5. **Keys are generated on the host at runtime** (agenthub's approach: never in git or the store; a rebuilt host makes new keys and permissions follow names, not keys). Supersedes [[docs/graph/261111230007-R007|Secrets architecture (Hybrid-1 default, Hybrid-2-ready abstraction)]]'s placement of "NATS auth" in the agenix infra layer. **Recorded alternative:** agenix-encrypted keys, for a future case where a key must survive host rebuilds.
6. **Non-thing identities:** bnox ships fixed identities for its own services (webhook receiver, dispatcher, sync/build units — this fixes G23) scoped to `host.deploy.>`; an `ops` identity with full access, root-readable only; host config may declare extra identities with their own permissions (e.g. agenthub's echo canary). The dispatcher moves off nats-py (G4) — agenthub's Go `deploy-bridge` is the reference.
7. bnox fills the implied `nats_seed` slot itself (absorbs the keygen).
