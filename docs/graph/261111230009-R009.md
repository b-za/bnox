# Hermes agent deviation (Q14 escape hatch used)

Converted from the archived decision log ([[docs/graph/261111230000-D005|converted archive decisions]]): `docs/archive/design/process/05-decisions.md` line 205, D-009 (accepted).

## Context

User wants to host a Hermes agent (Nous Research, MIT, v0.19.0) on the bnox system. Hermes is a long-running AI agent that connects outward to messaging platforms (Telegram, Discord, Slack, etc.) and LLM APIs. Its distribution model is fundamentally imperative: `curl|bash` install script, manages its own Python (via uv) and Node.js, downloads Playwright/Chromium, and **self-updates via `hermes update`**. Forcing it into a Nix-built container image would: break the auto-update model; require repackaging on every upstream release; require vendoring all Python deps, Playwright, Node, Chromium; be a multi-week effort that recurs every release. This is exactly the case the Q14 deviation clause ("a specific thing may deviate when it has a justified need; deviations are raised as an open question and logged as a decision before adoption") exists for.

## Decision

1. **Hermes is hosted as a `daemon`-shape thing with `host-install` runtime** (both new — see Q9.8 and Q9.9 below). It runs on host (not in a container), under a dedicated `hermes` user, managed by a systemd service that invokes Hermes' gateway.

2. **Deviation scope is narrow and explicit.** This decision authorises **only** that [[docs/graph/261111230002-R002|Container runtime and image-build policy]]'s "images must be Nix-built via `dockerTools.*`" rule does not apply to Hermes. Every other decision ([[docs/graph/261111230006-R006|Thing hosting architecture]] thing architecture, [[docs/graph/261111230007-R007|Secrets architecture (Hybrid-1 default, Hybrid-2-ready abstraction)]] secrets via `file` backend, Q9.6 user isolation, Q9.7 hardening bundle, Q14 default ceiling for all other things) applies to Hermes unchanged.

3. **bnox's role for Hermes:**
   - Creates the `hermes` user (Q9.6).
   - Provides `$HERMES_HOME` at `/var/lib/hermes/`, owned by `hermes`.
   - Runs the upstream install script once (manually, at provisioning) under the `hermes` user — NOT via Nix derivation.
   - Provides a systemd unit `hermes.service` that runs the gateway as `hermes`, with the standard Q9.7 hardening bundle plus network egress to required destinations (HTTPS outbound, DNS).
   - Provides secrets via [[docs/graph/261111230007-R007|Secrets architecture (Hybrid-1 default, Hybrid-2-ready abstraction)]] `file` backend at `/var/lib/bnox/secrets/hermes/<slot>`, chown'd to `hermes`.
   - Does NOT manage Hermes updates — `hermes update` is run by the operator (or a cron job) as the `hermes` user. bnox treats Hermes as a self-managing black box.

4. **Hermes manages its own:**
   - Code (git checkout at `/var/lib/hermes/hermes-agent/`)
   - Python virtualenv (managed by uv)
   - Node.js (downloaded by install script)
   - Playwright/Chromium
   - State, sessions, memory, skills (`$HERMES_HOME`)
   - Updates (`hermes update`)

5. **Justification logged per Q14:** Hermes' upstream distribution and auto-update model is the load-bearing fact. Fighting it with Nix packaging is a recurring multi-week cost. The deviation is visible (this entry) and scoped (only Hermes; only the image-build rule).

### Supporting refinements (locked alongside this decision)

### Q9.8 — New shape: `daemon` (refinement to [[docs/graph/261111230006-R006|Thing hosting architecture]], locked)

Locked alongside D-009. The shape taxonomy ([[docs/graph/261111230006-R006|Thing hosting architecture]]) gets a fifth entry: **`daemon`** — long-running stateful process; no inbound HTTP/NATS interface required; initiates outbound connections; may have its own state directory and update mechanism. Examples: AI agents (Hermes), bots, polling integrations, scheduled job runners. A thing can still be multi-component, so e.g. `daemon` + `http-api` is valid (background agent + HTTP control surface).

### Q9.9 — New runtime option: `host-install` (refinement to [[docs/graph/261111230006-R006|Thing hosting architecture]], locked)

Locked alongside D-009. The thing-hosting abstraction ([[docs/graph/261111230006-R006|Thing hosting architecture]]) implied `oci-containers`. Refinement: each component has an orthogonal `runtime` field — `container` (default, Nix-built image per [[docs/graph/261111230002-R002|Container runtime and image-build policy]]) or `host-install` (thing manages its own installation in its user space, bnox provides only the user + systemd unit + secrets slot + hardening). `host-install` is rare and requires a Q14 deviation per thing; Hermes is the first.

### Q14 — Over-engineering guardrail (resolved)

**Resolved 2026-07-27.** Captured as NFR-6 in `design/process/03-requirements.md` (to be added):

> **NFR-6 — Deployment simplicity ceiling (default; deviations allowed with justification).** Default: application-layer deployment (per [[docs/graph/261111230006-R006|Thing hosting architecture]]) is implementable using only **Podman, systemd, git, and optionally Forgejo**. Per-thing overhead **≤ 3 systemd units** (container + git-sync + build-trigger). Rollback via `podman load` of prior image + `systemctl restart` — no separate rollback tooling. By default forbidden: Kubernetes, Nomad, Argo CD, Flux, Helm, any framework with its own control plane. **A specific thing may deviate** when it has a justified need; deviations are raised as an open question and logged as a decision (D-NNN) before adoption — not silent.

D-009 (Hermes) is the first use of this deviation clause.

## Alternatives Considered

- **Nix-package Hermes properly:** rejected — recurring multi-week effort every release; breaks `hermes update`; Playwright packaging is notoriously painful.
- **Container with non-Nix image build (Option B):** rejected — corrupts [[docs/graph/261111230002-R002|Container runtime and image-build policy]] more broadly (the entire image build is non-deterministic, vs. just an install path on host); still breaks `hermes update` inside immutable image.
- **Don't host Hermes on bnox:** rejected — doesn't meet user's stated goal.

## Consequences Elsewhere

- [[docs/graph/261111230002-R002|Container runtime and image-build policy]] unchanged for all things except Hermes.
- Hermes appears in bnox host config as a `daemon`-shape thing with `runtime = "host-install"`.
- Hermes receives the standard Q9.6 user isolation + Q9.7 hardening bundle. Network egress restricted to required destinations (HTTPS, DNS) via systemd `IPAddressDeny=any` + `IPAddressAllow=`.
- Hermes' subagent sandbox backends (Docker, SSH, Singularity, Modal) are restricted to `local` only — no Docker socket exposure, no SSH backend. Configured in Hermes' config, enforced by absence of those capabilities in the systemd unit.
- Operator runs `sudo -u hermes hermes update` periodically (or schedules it via systemd timer). bnox does not manage Hermes version.
- The deviation is reviewed if Hermes' distribution model changes (e.g. they ship a Nix derivation or pre-built reproducible images).
