# Deployment dispatch topology (central dispatcher)

Converted from the archived decision log ([[docs/graph/261111230000-D005|converted archive decisions]]): `docs/archive/design/process/05-decisions.md` line 389, D-013 (accepted).

## Context

[[docs/graph/261111230011-R011|App-layer deployment mechanism]] §4 described the per-thing pipeline units as subscribing to NATS subjects directly ("`<name>-sync.service` — subscribes to `.changed`"; "`<name>-build.service` — subscribes to `.synced`"). A literal reading means **2 long-running subscriber daemons per thing** (sync + build), each idle-waiting for events. On a host with N things that is 2N+1 always-running processes (plus containers). User explicitly rejected this: "I don't want to end up with many running processes that are just waiting, rather have a central one that wakes the right one up when it needs to wake up."

## Decision

1. **One global `bnox-deploy-dispatcher.service`** is the sole subscriber to the `host.deploy.>` event namespace. It parses the thing name + event type from the subject and triggers the corresponding per-thing oneshot (`<name>-sync.service` on `.changed`; `<name>-build.service` on `.synced`).
2. **Per-thing sync/build units become oneshots** (`Type=oneshot`), woken by the dispatcher — not long-running subscribers. They do their work (git sync; nix build + podman load + restart) and exit.
3. **All events still flow through NATS** (`host.deploy.<name>.{changed,synced,built,deployed,failed}`) and the `host-deploy-logs` JetStream stream still captures the full audit trail ([[docs/graph/261111230011-R011|App-layer deployment mechanism]] §2/§3 observability intent preserved). The dispatcher is a router, not a replacement for the bus.
4. **Build invocation, rollback, subjects, and HMAC auth are unchanged from [[docs/graph/261111230011-R011|App-layer deployment mechanism]]** — only the dispatch topology changes.

## Alternatives Considered

- **Per-thing subscriber daemons ([[docs/graph/261111230011-R011|App-layer deployment mechanism]] §4 literal):** rejected by user — 2N+1 idle waiting processes; wasteful and noisy at rest.
- **Sync directly triggers build via `systemctl start` (no NATS hop between sync and build):** rejected — drops the `.synced` event from the bus, losing [[docs/graph/261111230011-R011|App-layer deployment mechanism]]'s step-by-step audit trail and the ability to observe/intervene between sync and build.

## Losing Readings

Each alternative's losing reading is given inline above, as recorded in the archive.

## Consequences Elsewhere

- Two global services instead of one: `bnox-webhook-receiver.service` (publishes `.changed`) + `bnox-deploy-dispatcher.service` (routes `.changed`/`.synced` to oneshots). Both are bnox-owned, not per-thing.
- Per-thing unit count: sync(oneshot) + build(oneshot) + container(s). Single-component thing = 3 units (NFR-6 ceiling honored); multi-component adds container units only (as [[docs/graph/261111230011-R011|App-layer deployment mechanism]] §5 already noted).
- Long-running process count is constant (2 globals) regardless of how many things run — scales cleanly. Trade: one more global service vs [[docs/graph/261111230011-R011|App-layer deployment mechanism]] §4's literal one; accepted as worth it.
- `modules/deployment/` gains a dispatcher concern (lives in `pipeline.nix` or a sibling `dispatcher.nix` — implementation choice for the pipeline job). [[docs/graph/261111230011-R011|App-layer deployment mechanism]] §4's unit descriptions are read as naming the *functional* units (sync, build, container), not mandating that each literally run a subscriber loop.
