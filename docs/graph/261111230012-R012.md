# Migration scope

Converted from the archived decision log ([[docs/graph/261111230000-D005|converted archive decisions]]): `docs/archive/design/process/05-decisions.md` line 355, D-012 (accepted).

## Context

Q5 asked whether bnox is for new systems only, retro-fits uqbn, or retro-fits snowi-node. User clarified: **bnox itself is the priority — finalize it as a standalone base first, without baggage from either source system.** Migration is a separate later phase, handled per-thing with a keep/migrate/toss decision for each. uqbn is the first migration target because the user wants to wipe the MacBook and replace uqbn with bnox, then selectively choose what to put on it (Hermes included; other uqbn content not critical and may be discarded). snowi-node migration is long-term, no urgency.

## Decision

1. **Phase 1 — Build bnox standalone.** Implement the base as specified by [[docs/graph/261111230001-R001|Project name]] through [[docs/graph/261111230011-R011|App-layer deployment mechanism]]. No source-system-specific code, no migration shims, no compatibility layers. bnox stands on its own.

2. **Phase 2 — Initial deployment.** Deploy bnox fresh on a new host (VPS / VM / fresh hardware). Validate the base works as designed, including hosting at least one thing end-to-end (likely Hermes, per [[docs/graph/261111230009-R009|Hermes agent deviation (Q14 escape hatch used)]]). uqbn and snowi-node stay untouched during this phase.

3. **Phase 3 — uqbn migration (per-thing).** Wipe the MacBook, install bnox, then evaluate each piece of uqbn content individually:
   - **Keep + migrate:** selected things moved onto bnox via the standard `.bnox/` pattern ([[docs/graph/261111230006-R006|Thing hosting architecture]]).
   - **Discard:** anything not worth migrating gets thrown in the bin. User has signalled most uqbn content is non-critical.
   - Hermes ([[docs/graph/261111230009-R009|Hermes agent deviation (Q14 escape hatch used)]]) is the first thing to host on the post-wipe MacBook.

4. **Phase 4 — snowi-node migration (long-term).** Deferred indefinitely. Each snowi-node service evaluated per-thing when the time comes. No urgency; not part of bnox's design.

## Alternatives Considered

- **Wholesale migration of either source system as a unit:** rejected per user — wants per-thing review, not bulk lift-and-shift.
- **snowi-node first:** rejected — production risk, two-major NixOS jump ([[docs/graph/261111230010-R010|NixOS version pin and channel choice]]), no immediate motivation.
- **Build migration tooling into bnox itself:** rejected — bnox is the base; migration is an operator activity, not base functionality.
